# Renderer and grid display audit

Audit date: 16 October 2026. Source baseline: `2.2.0-SNAPSHOT`, with the existing renderers held unchanged during the architecture cleanup. This is the pre-repair baseline: subsequently authorized algorithm corrections and their regression results must be tracked separately, without silently turning the observations below into passing evidence.

The rendering abstraction is reusable, but the catalog smoke test does not establish visual or semantic correctness. The audit confirms missing renderer text, incorrectly plotted statistical values, stale indicator geometry, mismatched ternary geometry, and defects in the optional grid batch path. These findings are a separate correction backlog; none requires modifying a renderer as part of the current Core dependency cleanup.

## Scope, method, and limits

The inventory covers every entry in [renderer-catalog.txt](../../../arbercharts-demo/src/main/resources/data/renderer-catalog.txt), the actual constructor and alias routing in `DemoApplication.buildSpecialRenderer()`, all eleven concrete Core grid layers, and the non-catalog `SignalIntegrityLayer` used by `ArberChartBuilder`. It also traces the five spatial renderers through the Swing and server dispatchers. Panel axes, legends, crosshairs, tooltips, and their UI layout are covered by the [companion UI audit](ui-report.md).

All **156 catalog entries now have focused static source coverage** of their actual implementation or traced inherited/alias path. Eleven entries additionally have independent command-level reproductions. The initial focused reviews address the specific behaviors in the findings below; the completion pass adds individual records for the remaining 102 entries, examining data access and logical counts, bounds and transforms, persistent state, styles/text, and relevant degenerate inputs. A source review establishes the observations recorded here, not correctness of every algorithm or branch. No screenshot comparison of the complete catalog was performed, and **no entry has a complete visual sign-off from this audit**.

The independent reproduction program was compiled and run with Java 25 in headless mode against the pre-cleanup, previously built shaded baseline:

```text
dist/releases/jvm/arbercharts-demo-2.2.0-SNAPSHOT.jar
```

It used a recording `ArberCanvas`, explicit plot ranges, and ordinary public models. Its output records actual emitted coordinates and colors, rather than inferring them from a rendered image. The unchanged renderer and grid sources were cross-checked against those results. This avoids depending on the server backend while that backend is being repaired. Retained evidence: [renderer harness](harness/ChartsRendererAudit.java) and [baseline output](results/renderer-baseline.txt). See the [reproduction instructions](README.md#reproduce-the-probes) for running it against a current built artifact.

The audit does not count the old server rasterizer's stroke-width or alpha behavior as an open renderer defect; that backend is being corrected separately. The full Maven verification is coordinated separately and is not claimed as a result of this independent investigation.

## Confirmed correction backlog

Priority P1 denotes incorrect plotted values or live data that should be fixed before relying on that renderer for data interpretation. P2 denotes a material missing visual behavior or broken optional path. The reproduction scope is stated for each finding.

### R1 — P1: Box plots do not draw the supplied quartiles or median

`BoxPlotRenderer.drawData()` reads `StatisticalChartModel.getIqr()` but reconstructs Q1/Q3 as `median ± IQR/2`, even though the typed model exposes both explicit quartiles. It also reuses `buf[1]` for the median line after that buffer has been overwritten with the lower-quartile mapping.

Reproduction: one box with `median=50, Q1=20, Q3=60, min=0, max=100`, in a 400-pixel-high plot spanning Y=0..100. The recording canvas receives the box between pixel Y=120 and 280 (values 70 and 30), and the median line at Y=280 (value 30). Correct landmarks are Q3 at Y=160, Q1 at Y=320, and median at Y=200.

### R2 — P1: Indicator caches retain old data when point count is unchanged

Several indicators return early when the model object and point count match, without checking `getUpdateStamp()`. Reusing a model after `clear()` and repopulating it to the same length therefore preserves old indicator values even though the model reports a newer update stamp.

Executable reproduction: render ATR with 50 points and a high/low spread of 4; clear the same `DefaultChartModel`, refill 50 points with a high/low spread of 40, and render with the same context and renderer. The update stamp changes from 50 to 101. The existing ATR emits exactly the old commands, whereas a fresh ATR emits different commands for the current data.

### R5 — P2: Ternary data, grids and spatial rendering disagree

The three ternary renderers and `TernaryGridLayer` use different triangles. In a 640×400 plot, `TernaryPlotRenderer` maps pure components to `(320,0)`, `(0,400)`, `(640,400)`. The grid vertices are `(320,24)`, approximately `(116.77,376)`, `(523.23,376)`. These differences were reproduced from actual draw commands. Points on the composition boundary therefore do not sit on the corresponding grid boundary.

`TernaryContourRenderer` uses a centered equilateral triangle and maps B to the right corner; the basic and phase renderers map B to the left corner. The phase renderer uses yet another margin-based triangle. These differences are source-confirmed, not a visual comparison of every mode.

There is also a separate active-path error: the basic renderer's Canvas path draws isolated octagons, while `renderSpatial()` streams the same points without path breaks or point marker styles. The harness records `moveFlags=true,false,false` and `markerId=0`. The actual frontend consumers join adjacent points into lines, and their line-only output path drops a single point. Thus the demo/server path does not preserve the renderer's scatter semantics.

### R10 — P2: Histogram geometry ignores the supplied axis range

`HistogramRenderer` derives bins from all model X values and normalizes their heights to its own maximum count, then places rectangles directly across the entire pixel bounds. It does not map the bin edges or counts through `PlotContext` and provides no preferred count range. Changing the context's X/Y ranges therefore does not change the data geometry, even though the surrounding axes may change.

Source-confirmed trigger: show the same sample model with two different explicit Y ranges, or zoom X to a subset of the samples. The bars remain normalized to the full plot rather than aligning with the requested numeric domain. Location: [HistogramRenderer.java:33](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/statistical/HistogramRenderer.java#L33)–[:50](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/statistical/HistogramRenderer.java#L50) and [:72](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/statistical/HistogramRenderer.java#L72)–[:97](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/statistical/HistogramRenderer.java#L97).

Required regression: assert bin edges and counts against a small known sample fixture, then check zoom/pan and count-axis labels together. If normalization is intended, it needs an explicit contract and matching axis-domain metadata.

### R11 — P2: Polar-family grid radii are inconsistent

The external `PolarGridLayer` uses radius `0.46 * min(width,height)`. `PolarRenderer`, `PolarLineRenderer` and `PolarAdvancedRenderer` draw internal grids/data with radius `0.425 * min(width,height)`; radar and wind rose use 0.4. ## Why existing visual tests do not catch these defects

`RendererSmokeTest` builds a 640×400 image with one demo model per catalog class. It filters out `PerformanceAuditRenderer`, allows blank output for four overlays, supplies custom Y windows for four indicators and extends X for three predictive renderers. `hasContent()` only asks whether any ARGB integer is nonzero. This catches a class that emits nothing but does not validate labels, correct values, plot alignment, updates, complete topology or direct/spatial equivalence. The existing `RendererVisualRegressionTest` covers eight renderers: Candlestick, Line, Pie, Radar, Heatmap, MedicalSweep, Volume and Donut. Its `hash != 0` assertion does not prove nonempty pixels: the harness computed CRC32 `4246071722` for a completely zeroed 640×360 ARGB raster. The next suite should combine small semantic fixtures with reviewed image references. Numeric assertions should establish quartiles, indicator values, data-space endpoints, model update behavior, topology and grid alignment. Images should then establish readable labels, spacing, contrast, stroke/alpha behavior, clipping, theme transitions and HiDPI appearance. ### Focused static review: statistical and analysis renderers

All 32 entries below were read through their actual drawing path and helpers. This is source inspection, not command execution or visual approval. **Confirmed** means the trigger and output effect follow directly from the implementation; **fixture** describes a future reproducible boundary check without claiming it has run. Production implementations were not changed.

Shared paths were also inspected: [BaseRenderer.render](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/BaseRenderer.java#L54) delegates directly without clipping or input sanitization; [theme and stroke helpers](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/BaseRenderer.java#L327) resolve current context/theme state; [pBuffer](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/BaseRenderer.java#L309) returns the same thread-local two-value array on repeated calls. [RendererAllocationCache](../../../arbercharts-core/src/main/java/com/arbergashi/charts/tools/RendererAllocationCache.java#L27) returns reusable arrays whose capacity can exceed the requested logical length and does not clear their contents. Unless a row says otherwise, each renderer recomputes its values and rewrites the used geometry prefix on every draw; the arrays cache storage, not a completed image or analysis result. None of these 32 drawing paths emits text. Axis labels and annotation text therefore require a separate frontend or overlay path.

The [ChartModel array contract](../../../arbercharts-core/src/main/java/com/arbergashi/charts/model/ChartModel.java#L43) distinguishes logical size from array capacity. The [default component contract](../../../arbercharts-core/src/main/java/com/arbergashi/charts/model/ChartModel.java#L224) falls back to Y; [DefaultChartModel](../../../arbercharts-core/src/main/java/com/arbergashi/charts/model/DefaultChartModel.java#L136) explicitly supplies `0=x, 1=y, 2=weight, 3=min, 4=max`. A renderer that expects lower/upper bounds or two channels needs a model providing those values; names alone do not supply statistical estimates.

#### Additional source-confirmed priorities

These are static deductions from the read paths, not newly executed reproductions. They complement the existing R1–R11 rather than replacing their recorded evidence.

- **P1 — Live statistical and topology caches omit content changes.** `ControlChartRenderer` and `ParetoRenderer` key cached results on Y-array identity/count; `DelaunayRenderer` keys edges on point count and plot rectangle. A normal full [CircularChartModel.getYData():220](../../../arbercharts-core/src/main/java/com/arbergashi/charts/model/CircularChartModel.java#L220) returns a stable array that [ensureSnapshot():504](../../../arbercharts-core/src/main/java/com/arbergashi/charts/model/CircularChartModel.java#L504) refills. After adding new samples, derived limits, sort totals or neighbor topology can describe old values while plotted points show current values. Extend R2's reused-versus-fresh fixture to these classes and to Delaunay's background completion.
- **P1 — Parallel Coordinates uses a positive lower bound as the initial maximum.** Both draw and hit paths initialize maxima with `Double.MIN_VALUE` at [59](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/specialized/ParallelCoordinatesRenderer.java#L59) and [131](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/specialized/ParallelCoordinatesRenderer.java#L131). Negative-only columns therefore use an absent near-zero value as their upper bound; a constant negative column is not centered. A one-dimensional model, accepted by the default model constructor, also divides axis spacing by zero.
- **P1 — Pareto order is not reflected in category positions.** Sorted indices choose original mapped X values for bars and cumulative points at [124](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/specialized/ParetoRenderer.java#L124) and [196](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/specialized/ParetoRenderer.java#L196). An unsorted three-category input produces a cumulative curve that goes backward in X. A later correction must coordinate reordered category labels with reordered positions.
- **P2 — Layout units omit or displace valid data.** Alluvial's fixed-three-column arithmetic overflows for four nodes; Dependency Wheel divides angles by edge count, collapsing a single two-node link; both Horizon variants allocate four full-height-quarter bands from the middle, exceeding the plot. These have exact triggers in their rows and require numeric landmark assertions before screenshot approval.
- **P2 — Valid constant Heatmap grids disappear.** The color minimum is also treated as an empty-cell threshold at [271](../../../arbercharts-core/src/main/java/com/arbergashi/charts/render/specialized/HeatmapRenderer.java#L271); all cells of a constant positive grid are skipped. Empty-density handling and explicit-grid color normalization need distinct fixtures.
- **P2 — Reduction changes the displayed endpoint or loses the tail.** Sparkline marks the final reduced bucket maximum rather than the last observation; Spectrogram's integer step does not span the full input unless sizes happen to align. Fixtures must include a distinctive last observation and assert its mapped position/color, not merely nonempty output.

For all rows, malformed/nonfinite-input fixtures are proposed coverage, not a claim that every listed shape defect occurs with the demo's current preset. The confirmed defects above state concrete accepted-input scenarios; remaining rows document implementation behavior and the next evidence needed for display refinement.
